#### (e) B2: la fuente local `trusted=yes` cuando `/srv/encina-repo` deja de cuadrar — las tres preguntas, en la misma VM y después de B1

**P3 (primero, porque no muta): ¿`apt` señala algo por `trusted=yes` en cada
`update`?** **No. Ni un aviso, rc 0.** Lo único que hace el repo plano local
son líneas `Ign:` de cortesía (busca `InRelease`/`Release`/`Translation-en`
que no existen, reintenta, y acaba en `Get:3 file:/srv/encina-repo ./
Packages [42.5 kB]`). Ningún «insecure», ningún «unsigned»: `trusted=yes`
apaga esa alarma, que es para lo que se puso (§4.15).

**P1: ¿qué dice `apt update` si el directorio se borra?** (se apartó con
`mv`, mutación verificada, y se restauró después, verificado):

```
Err:3 file:/srv/encina-repo ./ Packages
  File not found - /srv/encina-repo/./Packages (2: No such file or directory)
...
E: Failed to fetch file:/srv/encina-repo/./Packages  File not found ...
E: Some index files failed to download. They have been ignored, or old ones used instead.
rc_sin_directorio=100
```

**Es un ERROR, rc 100 — no un aviso—, y a la vez NO para lo demás:** las
cinco fuentes de red se refrescaron (`Hit:` todas) en esa misma pasada. El
precio real es doble: **cualquier guion que mire el rc de `apt update` se
rompe**, y los cuatro paquetes de Encina **se quedan sin candidato**
(`apt-cache policy encina-branding` → sólo `/var/lib/dpkg/status` a 100; el
«old ones used instead» no aplica a una fuente `file:` desaparecida).

**P2: un `encina-branding` MÁS NUEVO instalado a mano, ¿`full-upgrade` lo
respeta o lo baja?** Se fabricó `0.1.17+b2prueba1` reempaquetando el `.deb`
del repo local con `dpkg-deb` (sólo cambia `Version:`; para medir el
comportamiento de `apt` la versión es lo único que juega), se instaló, y:

```
 *** 0.1.17+b2prueba1 100
        100 /var/lib/dpkg/status
     0.1.17 500
        500 file:/srv/encina-repo ./ Packages
(full-upgrade no nombra a encina-branding: lo respeta)
```

**Lo respeta.** El instalado queda a prioridad 100 y el del repo local a 500,
y aun así `apt` no degrada sin `--allow-downgrades` o un pin > 1000: el
candidato es el instalado. Deshecho después (`0.1.17` restaurado del repo
local, verificado por `dpkg-query`).

**Lo que esto le dice a C2, sin decidirlo aquí:** dejar `encina-local.list`
para siempre no cuesta ruido (P3) y no pisa versiones más nuevas (P2); lo que
cuesta es que **la máquina queda atada a que `/srv/encina-repo` exista**: si
desaparece, cada `apt update` devuelve error (P1). Retirar la fuente tras
instalar cuesta perder la capacidad de reinstalar los cuatro `.deb` sin red.
La decisión es de la casilla C2 y ahora tiene las tres salidas delante.

#### (f) Mordidas de instrumento de esta sesión

- **`hdiutil attach` no monta el medio híbrido** («sistemas de archivos que
  no pueden montarse»); el núcleo y el `initrd` se sacaron con
  `xorriso -osirrox on -extract`.
- **`zsh` no parte una variable con la orden `ssh` dentro** (`no such file
  or directory: ssh -i ...`): el envoltorio fue un guion, no una variable.
- **Un `dpkg-query -f` con `${...}` a través de `ssh` + `sudo sh -c` llega
  con los campos vacíos** (dos veces): las comillas anidadas se comen los
  `${}`. Donde importó, la misma pregunta se hizo con `apt list
  --upgradable` o con el guion subido por `scp`, no tecleada en línea.
